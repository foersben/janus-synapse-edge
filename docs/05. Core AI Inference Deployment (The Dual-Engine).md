# Core AI Inference Deployment (The Dual-Engine)

The theoretical foundation of the Janus architecture relies on an asymmetric **"Dual-Engine"** inference topology. By orchestrating two fundamentally different inference engines across a single hardware substrate, we achieve both deep reasoning (System 2 thinking) and high-frequency reflex actions (System 1 thinking) without requiring costly, enterprise-grade server clusters.

These engines are deployed as high-performance Kubernetes Pods onto the Talos Linux compute worker VM, enjoying exclusive, low-overhead access to the physical GPU and CPU core topologies.

---

## 1. Engine A: The Deep Orchestrator (llama.cpp Speculative Decoding)

Engine A is responsible for high-level semantic planning, memory consolidation, multi-step task synthesis, and complex code generation. It hosts a massive **70-Billion parameter language model** (e.g., Llama-3-70B).

Running a 70B model at FP16 precision requires approximately $140\text{ GB}$ of VRAM, an impossibility on consumer-grade workstations. In the legacy 2024 architecture, we utilized PowerInfer to exploit activation sparsity (ReLU). However, top-tier modern reasoning models have transitioned to SwiGLU activation functions, rendering ReLU-specific sparsity models obsolete.

To resolve the memory bottleneck, the 2026 Janus stack deploys **llama.cpp** configured with **Draft-Model Speculative Decoding**:

### 1.1 The Speculative Execution Pipeline

1. **4-Bit GGUF Quantization:** The base 70B parameter model is compressed using 4-bit quantization (GGUF), shrinking the physical storage footprint to roughly $35\text{ GB}$ with negligible reasoning degradation.
2. **VRAM-Resident Draft Model:** A lightweight, highly responsive draft model (e.g., Llama-3-8B quantized aggressively) is loaded entirely within the primary compute node's GPU VRAM, occupying a portion of a strict **$11\text{ GB}$ VRAM allocation**.
3. **Speculative Guessing:** The draft model guesses multiple consecutive tokens inside the GPU VRAM at high speeds, completely bypassing the physical PCIe bus bandwidth bottleneck.
4. **Physical P-Core Verification:** The 70B base model weights reside in the workstation's $128\text{ GB}$ system DDR5 RAM, bound via Talos hugepages to prevent OS-level cache eviction. The **8 physical P-Cores** of the Intel i7-14700K execute a parallel verification pass, batch-verifying the draft model's guessed tokens.
5. **Operational Latency Result:** By converting a memory-bandwidth-bound sequential problem into a compute-bound batch verification task, Engine A sustains **$15\text{-}20\text{+ tokens/second}$** on a 70B model operating out of DDR5 system RAM, avoiding CPU thermal throttling and keeping PCIe lanes unsaturated.

### 1.2 Kubernetes Resource Allocation (The Hugepages Lock)

To prevent the Kubelet from miscalculating available standard RAM and throwing the pod into a perpetual `Pending` state, the Kubernetes manifest must explicitly request the 1GB hugepages allocated by the Talos guest OS. Standard memory is reserved solely for container overhead.

```yaml
resources:
  requests:
    nvidia.com/gpu: "1"
    memory: "4Gi" # Standard DDR5 for container overhead and KV-cache
    hugepages-1Gi: "35Gi" # The physical lock for the 70B GGUF weights
  limits:
    nvidia.com/gpu: "1"
    hugepages-1Gi: "35Gi"
```

## 2. Engine B: The Multimodal Reflex Agent (Qwen2-VL)

Engine B functions as the high-velocity tool-caller and visual data extractor. To support visual web-scraping without violating the strict **4.5GB** static VRAM fence on the RTX 5070 Ti, Engine B utilizes a heterogeneous split via `llama.cpp`.

By decoupling the LLM "brain" from the Vision Encoder "eyes," we protect the GPU's context window from massive image-patch memory spikes.

### 2.1 The Heterogeneous Hardware Split

1. **The LLM Brain (GPU):** The 4-bit quantized text weights (approx. 4.2GB) of Qwen2-VL-7B are loaded entirely into the RTX 5070 Ti. Standard text generation and coding tasks execute natively on the GPU at maximum velocity.
2. **The Vision Encoder (CPU):** The Multimodal Projection layer (`mmproj`) is strictly pinned to the i7-14700K and system DDR5 RAM (pre-allocated from the Hugepages pool via Kubelet).
3. **Asymmetric KV Cache Quantization:** To maximize the 4.5GB VRAM fence for Qwen2-VL multimodal ingestion, Engine B utilizes asymmetric caching natively via llama.cpp. The Key (K) cache is held at `q8_0` precision to preserve strict Letta JSON structural routing, while the Value (V) cache is aggressively compressed to `q4_0`. This reduces the context memory footprint by over 60%, allowing 32K context windows entirely within the GPU.

### 2.2 Kubernetes Deployment Arguments

The `llama.cpp` container must be executed with the following arguments to enforce this architectural split:

```yaml
args:
  - "-m"
  - "/models/qwen2-vl-7b-instruct-q4_k_m.gguf"
  - "--mmproj"
  - "/models/qwen2-vl-7b-mmproj-f16.gguf"
  - "--n-gpu-layers"
  - "99" # Forces all text layers into the 4.5GB VRAM fence
  - "-c"
  - "32768" # Restricts text context size
  - "--flash-attn" # Mandatory for Blackwell SM120 KV-cache stability
  # NOTE: We deliberately omit any vision-offload flags, forcing the mmproj to execute via system CPU/RAM.
```

### 2.3 Whisper STT GPU Offloading

To achieve ultra-low-latency Speech-to-Text (STT) translation without starving the E-cores on VM 2, the `whisper.cpp` server is deployed with CUDA acceleration on VM 1 (Tensor Worker).

* **VRAM Allocation:** The Whisper server pod is allocated a strict VRAM limit of `0.5 GB` within the GPU time-slicing configuration.
* **Execution Profile:** Translation runs on-demand, leveraging the RTX 5070 Ti CUDA cores. Under Blackwell-era tensor optimizations, a typical WebRTC audio packet is decoded and translated in under $100\text{ ms}$, routing the resulting text tokens directly to the TensorZero Gateway. This removes the CPU-bound E-core bottleneck and ensures the reflex conversational loop operates in near real-time.

## 4. Storage Architecture (OpenEBS LocalPV & io_uring)

Because the cluster consists of a single physical workstation, deploying complex distributed storage arrays (e.g., Longhorn or Ceph) introduces unnecessary scheduling overhead, SSD write-wear, and filesystem latency. Instead, we deploy **OpenEBS LocalPV** to map raw host paths directly to Kubernetes Persistent Volumes.

!!! warning "Magnum IO GPUDirect Storage (GDS) Incompatibility"
    True NVIDIA Magnum IO (GPUDirect Storage) permits the GPU to bypass the CPU and system RAM entirely, streaming model tensors directly from the physical NVMe controller via peer-to-peer DMA.

    However, because the primary Seagate FireCuda 530 SSD is secured at the bare-metal block level via **LUKS Block Encryption**, the Proxmox kernel must actively intermediate the decryption path. Consequently, GPUDirect Storage is topologically incompatible with the secure cryptographic boundary of the Janus architecture.

### 4.1 The Security-Latency Trade-Off

We deliberately sacrifice GPUDirect Storage to maintain absolute block-level physical data encryption. OpenEBS LocalPV utilizes standard virtualization interfaces (`virtio-blk`) pointing directly to the $1\text{M}$ `volblocksize` ZFS volume (ZVOL) on the host:

* **Asynchronous io_uring Paging:** To mitigate the virtualization penalty, the Talos Linux guest OS leverages `io_uring` to load GGUF weights and Letta archival states asynchronously.
* **Loading Speed:** Reading a $35\text{ GB}$ GGUF matrix into system DDR5 RAM via decrypted `io_uring` pipelines saturates physical SSD throughput at $3,500\text{ MB/s}$ to $4,500\text{ MB/s}$.
* **Performance Impact:** A cold boot of Engine A requires approximately $8\text{ seconds}$. While this is double the theoretical GPUDirect Storage (GDS) capability, it is the physical mathematical limit of fetching $35\text{ GB}$ through a standard virtualization interface. Because the model weights are physically pinned to RAM via the `hugetlbfs` 1GB hugepages (rendering them strictly unswappable by the Linux kernel), storage performance becomes irrelevant after boot, and active token generation speed is unaffected.

### 🛠️ Verification and Safety Checklist

!!! safety "Dual-Layer 1GB Contiguous Page Enforcement"
    Memory fragmentation must be neutralized at both the hypervisor and guest levels. While Proxmox backs the VM memory via KVM arguments, the primary Talos guest OS worker must also be configured to partition that memory for Kubernetes by injecting `hugepagesz=1G hugepages=84` into the kernel command line within `talos-machineconfig.yaml`. This specific geometry prevents TLB thrashing when mapping the monolithic 35GB llama.cpp GGUF weights, completely neutralizing OS paging pauses.
!!! danger "Blackwell Flash Attention Protocol"
    Both Engine A and Engine B must be strictly launched with the `--flash-attn` argument. Utilizing native FlashAttention-2 kernels is mathematically mandatory on the NVIDIA Blackwell (SM120) architecture to prevent KV-cache memory fragmentation and ensure sub-millisecond context paging during dynamic tool-calling loops.
