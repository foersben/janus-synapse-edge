# Observability, Telemetry, and GitOps

An autonomous, multi-agent AI cluster operating on constrained edge hardware functions essentially as a "black box." If an agent executes an infinite loop burning through 50,000 tokens during a nocturnal macro-downtime phase, or if the Intel i7-14700K approaches thermal junction limits during evolutionary training, precise telemetry is required for diagnosis.

Furthermore, iterative algorithmic updates generated by the cluster must be deployed via a deterministic, version-controlled pipeline that protects the delicate VRAM state.

---

## 1. LLM Tracing and Agent Observability

Standard terminal logs (`stdout`/`stderr`) are fundamentally insufficient for tracing the non-linear "thought processes" of autonomous agents. The architecture standardizes on **Langfuse** for granular execution observability.

* **Deployment Substrate:** The Langfuse container is deployed within the Kubernetes cluster, persisting trace data to a lightweight, localized Postgres pod.
* **Unified Telemetry Ingestion:** The `LiteLLM` proxy is configured to natively export all API requests, latency metrics, and token expenditures directly to Langfuse.
* **MCP Tracing:** Because the NemoVision system operates as an isolated Model Context Protocol (MCP) server within the Outbound DMZ, Langfuse spans are specifically configured to capture and trace the extracted visual DOM data before it is ingested by the core agents.
* **The Waterfall UI:** Langfuse generates a visual "Waterfall" trace. This allows the human operator to chronologically debug complex behaviors (e.g., observing exactly what Agent Zero planned, the specific Python parameters NemoClaw executed, and the precise millisecond latency of each sub-step).

## 2. Bare-Metal and Network Telemetry

Pushing a Micro-ATX thermal envelope and relying on a distributed, asynchronous storage subsystem (the UPS-backed Intel NUC) necessitates strict hardware monitoring.

We deploy `node-exporter` on both the bare-metal Proxmox host and the Debian NUC, feeding a centralized Prometheus/Grafana stack within the K3s cluster.

### 2.1 Mission-Critical Grafana Dashboards

The following custom dashboards are mandatory for cluster stability:

1. **PowerInfer Sparsity Monitor:** Tracks PCIe bus bandwidth utilization. This verifies that Engine A is correctly pinning "Hot" NVFP4 neurons inside the RTX 5070 Ti's VRAM while smoothly spilling "Cold" neurons to the Talos Hugepages without catastrophic latency spikes.
2. **VRAM Saturation Fences:** A critical alarm is configured to trigger if Engine B (`SGLang`) breaches 98% VRAM allocation. This allows the operator to dynamically adjust the `max_tokens` context limits before an Out-of-Memory (OOM) kernel panic occurs.
3. **P-Core Thermal Analytics:** Explicitly monitors the thermal diodes of Cores 0-7 (The P-Cores) on the 14700K.
   > !!! warning "Thermal Throttling Failsafe"
   > If sustained temperatures exceed 95°C during multi-hour AlphaEvolve training loops, the PL1/PL2 wattage limits must be manually lowered within the ASRock motherboard BIOS to prevent silicon degradation.
4. **Edge-Node Latency Tracking:** Monitors the 2.5G network switch traffic and ICMP latency to the Intel NUC. If SurrealDB asynchronous micro-writes exceed a 5ms latency threshold, it indicates a critical network congestion event that will inevitably bottleneck the inference engines.

## 3. GitOps, Hot-Reloading, and Mono-Repo Architecture

The AI software landscape evolves rapidly. Manual interventions (e.g., executing `kubectl apply` or establishing SSH sessions) introduce configuration drift and are strictly prohibited. The cluster is governed by a declarative GitOps Mono-Repo, sharply dividing Infrastructure logic from Agent logic to protect inference memory caches.

### 3.1 The Mono-Repo Structure
The entire cluster state exists as plain text YAML and Python files stored in a localized Gitea repository. **ArgoCD** continuously polls this repository and synchronizes state changes to the Kubernetes cluster.

* `/infrastructure`: Contains bare-metal configurations (e.g., `talos-machineconfig.yaml`).
* `/cluster-tools`: Contains foundational operator manifests (ArgoCD, NVIDIA device plugins, OpenEBS).
* `/apps`: Contains the core immutable engines (PowerInfer, SGLang, LiteLLM, n8n, AnythingLLM).
* `/agents`: Contains the dynamic, frequently mutating logic (Python tool scripts, CrewAI personas, system prompts).

### 3.2 The Atomic Update Flow (Protecting the VRAM Cache)

When the autonomous AlphaEvolve pipeline generates a superior algorithm, it autonomously commits the code to the Gitea `/agents` directory. ArgoCD must deploy this update without disrupting the operational cluster.

!!! success "The Hot-Reloading Advantage"
    When ArgoCD detects an update in the `/agents` directory, it explicitly avoids restarting the inference engine containers.

    Instead, ArgoCD synchronizes the new Python scripts or text files into a Kubernetes `ConfigMap`. The agent execution pods mount this ConfigMap as a live directory volume. The agents instantly "hot-reload" the new logic into memory. This architecture completely prevents the massive VRAM Cache-Augmented Generation (CAG) from being flushed, ensuring zero cold-start penalties during high-frequency autonomous training cycles.
