# Multi-Tenant Profiles and Privacy Tiers

Operating a centralized AI cluster that services both highly sensitive personal queries and generalized professional development tasks requires strict "Brain-Mixing" prevention. The Janus architecture enforces software-defined multi-tenancy at the memory substrate, gateway routing, and network egress layers.

---

## 1. Epistemological Isolation (Letta & Hindsight 2.0)

To prevent an autonomous agent from bleeding context between operational profiles (e.g., pulling a personal financial record while generating public Python code for a client), strict separation is enforced at the memory substrate level:

*   **Discrete Letta Agent Sandboxes:** SurrealDB's legacy namespace scoping is formally retired. In the 2026 stack, epistemological isolation is enforced by **independent Letta agent states**. Each user or operational profile runs a completely isolated Letta agent instance, which maintains its own scoped Core, Recall, and Archival token-spaces. It is computationally impossible for one agent's thread to query the memory buffer of another.
*   **Hindsight 2.0 Entity Scoping:** The Hindsight proxy filters semantic vector and graph retrieval requests. During lookups, Hindsight matches the request strictly to the tenant's specific **Letta Archival database partition**. This guarantees that subjective opinions, facts, and memories are never cross-contaminated between profiles.

---

## 2. Software-Defined Egress Governance

We categorize all incoming workloads into distinct "Sensitivity Tiers" to determine internet egress authorization:

### Tier 0: The "Private" Enclave

*   **Workload Scope:** Highly personal datasets, private system financial logs, credentials, or sensitive developer profiles.
*   **Routing Enforcement:** These tasks are hard-routed by the **TensorZero Gateway** exclusively to **Local Inference Only (Engine A or Engine B)**.
*   **Network Execution:** The declarative `tensorzero.yaml` configuration for Tier 0 profiles contains a hardcoded local provider block. It is mathematically impossible for data processed in this tier to traverse the external WAN gateway; it never leaves the secure, local 2.5G backbone.

### Tier 1: The "Professional" Enclave

*   **Workload Scope:** General developer tasks, boilerplate code generation, or public API research.
*   **Routing Enforcement:** Tasks in this tier are permitted to utilize remote, high-capacity commercial LLMs (e.g., Anthropic Claude, OpenAI).
*   **Sanitization:** Before the prompt payload is permitted to leave the cluster, it must pass through two strict, non-blocking pre-processors in the Rig orchestration plane:
    1.  **PII Masking Filter:** Algorithmically redacts identifiable names, IP addresses, and local system paths.
    2.  **Hindsight Tag Filter:** Only context nodes and entity relationships explicitly tagged as `privacy: public` in the local Letta Archival ledger are allowed to be appended to the outgoing API payload.

!!! danger "The Danger of Egress Misconfiguration"
    If the Hindsight Tag Filter fails, an autonomous agent could accidentally inject a private API key or local database credential from its long-term memory into an outbound Anthropic request. The two-stage sanitization pipeline is mandatory for all Tier 1 execution.

## 3. Resource Suitability and Temporal Priority

All AI reasoning (Engine A and Engine B) executes within the **Talos compute worker VM** to access the RTX 5070 Ti and the P-Core allocation. Because physical cores cannot be deeply partitioned between multiple active tenants without destroying inference latency, priority is managed via temporal Kubernetes preemption.

| Architectural Component | Hardware Allocation | Multi-Tenant Suitability and Execution Priority |
| :--- | :--- | :--- |
| **Intel P-Cores (0-15)** | **Critical Engine** | Hosts all bare-metal inference. Interactive human chats (`PriorityClass: System-Critical`) instantly preempt background agent processes (`PriorityClass: Background-Yield`), granting exclusive physical core access to the active tenant. |
| **Intel E-Cores (16-25)** | **Support Mesh** | Pinned strictly to the Orchestration Layer (**TensorZero Gateway, Rig Framework, Wasmtime Tool Sandbox, K3s Control Plane**), mapping to threads 16-25 and leaving threads 26-27 reserved for hypervisor decryption and storage overhead. |
| **128GB DDR5 RAM** | **Capacity Superpower** | Vast capacity permits the $70\text{B}$ GGUF model hugepages to remain permanently resident in memory, and Letta archival pages to stream asynchronously via `io_uring` without cold-start switching latency. |
| **RTX 5070 Ti VRAM** | **The Narrow Bottleneck** | The 16GB VRAM limit is the most constrained resource. Strict layer and context fencing via `llama.cpp` arguments ($11\text{ GB}$ Engine A / $4.0\text{ GB}$ Engine B / $0.5\text{ GB}$ Whisper STT) is enforced to prevent VRAM Out-of-Memory (OOM) kernel panics, permanently preserving the $0.5\text{ GB}$ ($500\text{ MB}$) system buffer reserved for Talos and headless CUDA context overhead. |

### 🛠️ Privacy and Tenancy Checklist

!!! safety "WASM Sandboxing Separation"
    Each tenant profile's tool execution must run in its own dedicated, transient Wasmtime instance. Sharing Wasmtime handles between distinct tenant agents is strictly banned to prevent cross-profile data leakage.
!!! warning "PII Redaction Overrides"
    Any custom prompts mutated by the GEPA prompt evolution pipeline must be verified against the TensorZero gateway schemas to guarantee they do not accidentally bypass PII masking filters.
