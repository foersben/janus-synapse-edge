# 04. Virtualization & Kubernetes (Talos + K3s)

## 1. Why Talos Linux?

Standard Ubuntu Server is bloated, uses too much RAM, and has a massive attack surface. We will use **Talos Linux**, an immutable, API-driven OS built specifically to run Kubernetes. It has no SSH, no console, and idles at under 500MB of RAM, reserving maximum resources for your AI.

## 2. Slicing the Hardware (VM Provisioning in Proxmox)

We will create two specific Virtual Machines.

### VM 1: The "Tensor Worker" (Heavy Lifting)

*This VM runs the inference engines and gets the direct hardware.*

* **CPU:** 8 Cores. Set type to `host` to inherit Intel AVX2 instructions. Pin this VM strictly to the 14700K's P-Cores (`taskset -c 0-15` on the Proxmox host).
* **RAM:** **84 GB** (Reduced to leave an 8GB unallocated hardware buffer on the host). Disable memory ballooning.
* **Disk:** 500 GB (Provisioned on the 1M ZFS recordsize dataset for massive model weights).
* **Hardware Passthrough:** Add a `PCI Device` and select the ZOTAC RTX 5070 Ti. Check `All Functions`, `ROM-Bar`, and `PCI-Express`.

### VM 2: The "Brain & Memory" (Control & Storage)

*This VM runs the proxies, orchestrators, and the Kubernetes Control Plane.*

* **CPU:** 10 Cores. Pin this VM strictly to the E-Cores (`taskset -c 16-25`).
* **RAM:** 24 GB. Disable memory ballooning.
* **Disk:** **100 GB** (Reduced from 1000GB, as the heavy database write loads have been offloaded to the external NUC).

## 3. Kubernetes Cluster Architecture (K3s)

Once Talos is installed on both VMs via its bootstrap ISO, initialize the K3s cluster.

* **The Control Plane:** VM 2 acts as the Kubernetes master node AND a general worker node.
* **The GPU Node:** VM 1 joins as a worker node.
* **Taints & Tolerations:** You must "taint" VM 1 in Kubernetes with `gpu=true`. This acts as a firewall within the cluster, ensuring that a random background task (like an n8n webhook) never accidentally spins up on the Tensor Worker and steals CPU cycles away from your AI models. *Crucial Rule:* Any pod that legitimately requires the GPU (like Engine A, Engine B, and the NemoVision MCP pod) MUST have a matching `toleration` explicitly written into its YAML manifest, otherwise it will sit in a `Pending` state forever
* **etcd Resilience (The Brain Backup):** Because the main server lacks a UPS, an abrupt power loss during an `etcd` write can corrupt the Kubernetes cluster state.
  * Configure K3s to take automatic `etcd` snapshots every 3 hours.
  * Do not store these locally. Configure the snapshot target as an S3-compatible bucket (MinIO) hosted on the **UPS-backed Intel NUC**.
  * If the server boots and Talos detects a corrupted `etcd` state, use the `--cluster-reset` flag linked to the **NUC's IP** to automatically pull the last known good state, ensuring the cluster self-heals without manual rebuilding.

## 4. Guest-OS Hugepages (Talos MachineConfig)

Instead of locking Hugepages on the bare-metal Proxmox host, we delegate memory management directly to the Talos Guest OS. This bypasses the severe performance penalty of mounting a bare-metal host directory into a virtualized Kubernetes pod.

When generating your `talos-machineconfig.yaml` for VM 1 (The Tensor Worker), you must explicitly append the kernel arguments to lock the **56GB** of memory into 1GB contiguous blocks at the guest level.

```yaml
machine:
  kernel:
    args:
      - default_hugepagesz=1G
      - hugepagesz=1G
      - hugepages=56# 04. Virtualization & Kubernetes (Talos + K3s)
```

* **The Workflow:** When VM 1 boots with its 84 GB of provisioned RAM, the Talos kernel immediately locks 56 GB of it. When Engine A (`PowerInfer`) deploys, it requests a Kubernetes volume mount using `emptyDir` with `medium: HugePages`, pulling pristine memory directly from the guest OS
