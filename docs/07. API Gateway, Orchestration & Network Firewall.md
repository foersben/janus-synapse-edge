# 07. API Gateway, Orchestration & Network Firewall

*Never let an AI agent talk directly to the internet, and never let the internet talk directly to your inference engines. We need a secure demilitarized zone (DMZ).*

## 1. LiteLLM Proxy (Internal Traffic Cop)

This container acts as the unified OpenAI-compatible endpoint for your entire network. No UI or agent is allowed to query `PowerInfer` or `SGLang` directly.

* **Semantic Routing (Saving Compute):** LiteLLM evaluates prompt complexity to protect your hardware:
    * **Engine B:** Routes simple formatting, fast logic, or continuous tool-calling to the ultra-efficient 7B-8B NVFP4 model sitting natively in the GPU's VRAM.
    * **Engine A:** Routes deep coding or complex planning to the PowerInfer 70B orchestrator to leverage sparsity offloading and save PCIe bandwidth.
* **Guardrails & Infinite Loop Protection:** To prevent autonomous agents from "runaway" behavior:
    * **Velocity Limits:** LiteLLM monitors token velocity via a sliding window; if it detects human-impossible speeds (indicating an infinite loop), it severs the connection and **alerts you via n8n**.
    * **Context Capping:** Hard-caps `max_tokens` for Engine B to ensure SGLang never spikes past its **4.5GB VRAM fence**. This strictly protects the final 1GB of VRAM for Talos and CUDA system overhead.
* **Query Batching (Network Optimization):** To fully utilize the **2.5Gbps link** provided by the Netgear MS308E and UGREEN adapter, LiteLLM and NemoClaw are configured to batch SurrealDB queries. This reduces TCP handshake overhead and prevents the network from bottlenecking GraphRAG performance.
* **Multi-Tenant Priority & Privacy Routing:**
	* **Privacy Tiers:** LiteLLM enforces "Egress Tiers". High-sensitivity profiles (Tier 0) are hard-locked to local inference pods (Engine A) with total egress blocks. Professional tasks (Tier 1) may route to external APIs only after PII masking and Hindsight tag-filtering.
    * **Priority Execution:** Interactive chat sessions are assigned `priority: 1` (System-Critical), while background agent loops are assigned `priority: 2` (Background-Yield). When a human user initiates a chat, LiteLLM triggers Kubernetes to instantly pause/preempt background tasks on the P-Cores, granting the human user immediate, zero-latency access to the GPU.

## 2. n8n (The Inbound DMZ)

Your Talos VMs, LiteLLM proxy, and AI models have no public IP addresses and no open outbound firewall ports. n8n is the only authorized bridge for incoming external requests.

* **Deployment:** Deployed via ArgoCD into your Kubernetes cluster, utilizing a lightweight Postgres pod strictly for workflow state persistence.
* **The Webhook Wall:** If you want to trigger an agent via your phone (e.g., sending a Telegram message or an email), that message hits a secure n8n webhook.
* **Sanitization:** n8n strips the payload of any malicious code, reformats it into a clean JSON object, and makes an internal cluster API call to LiteLLM.
* **Execution & Return:** LiteLLM routes the task, Engine B executes it, returns the output to n8n, and n8n sends the response back to your phone. The core AI itself never initiated an outbound connection.

## 3. WebRTC & Voice-to-Voice Gateway (LiveKit)

To upgrade the gateway from pure text/JSON to "Ultra-Low-Latency Voice", we bypass traditional text-to-speech pipelines.

  * **LiveKit Pod:** Deploy a WebRTC server as a Pod in your K3s cluster.
  * **Native Audio:** Engine B (SGLang) loads a native speech-to-speech multimodal model (e.g., Llama-3-Audio or an open-source Moshi equivalent). It processes raw audio waveforms directly, bypassing the latency of traditional Speech-to-Text (STT) and Text-to-Speech (TTS) steps.
  * **The Workflow:** Using a mobile app, you establish a secure, persistent WebRTC audio stream to the server. You converse with your agents just like a Discord call. If you interrupt the AI by speaking over it, Kubernetes routes the signal to SGLang, halting token generation in under 50ms (leveraging RadixAttention state drops) and immediately listening to your new command.

## 4. The NemoVision MCP Bridge (The Outbound DMZ)

When an internal agent (like NemoClaw) needs to read a live Single-Page Application (SPA) or scrape data, it is strictly forbidden from making an HTTP request. Instead, it delegates the task via the Model Context Protocol (MCP).

* **The MCP Server Pod & Tolerations:** NemoVision is deployed to **VM 1 (Tensor Worker)** to utilize the RTX 5070 Ti hardware for fast visual rendering. Because VM 1 is tainted, the NemoVision deployment YAML must explicitly include a `toleration` for `gpu=true`. It is strictly isolated within a dedicated `outbound-dmz` Kubernetes Namespace
* **Zero-Trust Egress/Ingress Policies:** By applying a Kubernetes `NetworkPolicy`, we create a software-defined air-gap. The NemoVision pod is granted egress internet access (whitelisted via strict DNS to domains like `.github.com` or your specific targets), but its internal ingress/egress is tightly locked to port `stdio/HTTP` solely for the MCP bridge. If the headless browser is compromised via a malicious webpage, the attacker is trapped inside the container with no network routes to the database (VM 2) or the Proxmox host.
* **The Air-Gapped Workflow:**
  1. NemoClaw (Internal) realizes it needs data from a website.
  2. It formats a standardized MCP request: `{"tool": "browser_extract", "url": "https://target.site", "target_element": "pricing_table"}`.
  3. The request crosses the internal cluster network to the NemoVision MCP pod.
  4. NemoVision (powered by the **Nemovision-4B-Instruct** SLM) executes the request, visually renders the JS/HTML, and extracts *only* the requested text data from the screen.
  5. NemoVision returns a sanitized JSON string back through the MCP bridge. The core AI never touches the raw HTML or malicious external scripts
