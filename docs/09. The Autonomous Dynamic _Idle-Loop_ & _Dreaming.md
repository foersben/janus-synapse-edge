# 09. The Autonomous Dynamic "Idle-Loop" & "Dreaming" Pipeline

*This layer abandons rigid clock-based cron jobs. Because your work hours are irregular, the system utilizes an Event-Driven architecture to instantly capitalize on micro-downtimes (getting food, running errands) and macro-downtimes (sleeping, sick days) while ensuring immediate resource yielding the second you return to work.*

## 1. The Two Pillars of Idle-State Optimization

### Pillar A: "Dreaming" (Memory Consolidation)

* **Driver:** SurrealDB 3.0 (Spectron Subsystem).
* **Hardware Target:** Intel NUC (Edge-Node) via Gigabit LAN.
* **Function:** Analyzes daily logs to infer implicit relationships in the knowledge graph. The heavy compute happens on the NUC's CPU and RAM buffer, completely offloading the main server.

### Pillar B: "Training" (Prompt/Skill Refinement)

* **Driver:** DSPy + Woodpecker CI.
* **Hardware Target:** Main Server (8 P-Cores + 128GB RAM + RTX 5070 Ti NVFP4).
* **Function:** Sandboxes past tasks, mutates prompts, and attempts to find faster, more token-efficient pathways using your Dual-Engine setup.

### AlphaEvolve & DSPy (Prompt & Code Optimization)

Based on the "AlphaEvolve" methodologies from early 2026, we do not limit the idle phase strictly to DSPy prompt optimization; we allow for **Evolutionary Coding**.

  * **Code-Level Mutation:** The Meta-Agent (Engine A / PowerInfer) takes the actual Python source code of your worker agents (e.g., NemoClaw's tool scripts or RAG routing logic) and uses LLM-mutation to rewrite the programmatic structure.
  * **Evaluation & Survival:** The generated code is tested against historical tasks (pulled from the NUC) inside an isolated Woodpecker CI sandbox, executed rapidly by Engine B (SGLang).
  * **Auto-Commit:** If the new algorithm beats the baseline (fewer tokens used, zero errors), the agent commits its own new Python code to your local Gitea instance, triggering ArgoCD to push the update live.

### The *Auto-Research* Idle Workflow

Inspired by autonomous research loops, this is how the server improves itself while you sleep:

1. **The Trigger:** A lightweight script monitors Prometheus. If P-Core and GPU utilization drop below 10% for more than 45 minutes, the Idle-Loop initiates.
2. **Task Extraction:** The loop pulls a historical, successfully completed task from SurrealDB over the LAN (e.g., "Agent successfully wrote a weather scraper using 4,000 tokens").
3. **The Mutation Matrix:** DSPy spins up 3 parallel instances of your NemoClaw executor. It mutates the system prompt or tool code for each instance.
4. **Execution & Verification:** The 3 instances attempt the exact same task in the Woodpecker CI sandbox. All traffic routes through LiteLLM to record the metrics.
5. **The Autonomous Commit:** If Instance B achieves the exact same verified result but only used 2,500 tokens, DSPy automatically pushes a Git commit. The next morning, your agent is tangibly faster and cheaper to run.

## 2. The Telemetry Trigger Engine (How it knows you are gone)

Instead of a clock, a lightweight Python watcher daemon runs inside your Kubernetes cluster, continuously polling **Prometheus** and your network for presence.

**The Trigger Conditions (It must pass ONE of these to initiate):**

1. **The Telemetry Threshold:** Prometheus reports <5% CPU/GPU utilization and zero LiteLLM API requests for exactly **45 uninterrupted minutes**.
2. **Network Presence (Optional/Advanced):** n8n polls your home router. If your phone's MAC address disconnects from the Wi-Fi (indicating you left the house), it overrides the 45-minute wait and triggers the idle loop within 5 minutes.
3. **The Manual Override:** A simple "Away Mode" button in your AnythingLLM UI that fires an n8n webhook, instantly putting the server into deep-training mode.

## 3. The Preemptive Scheduler (The "Wake Up" Protocol)

The biggest risk of dynamic idle-loops is that you return from grocery shopping, ask your AI a question, and the server is completely frozen because it's in the middle of a massive DSPy training run.

**Kubernetes `PriorityClass` Implementation:**
We solve this using Kubernetes Preemption.

* Your primary AI pods (LiteLLM, Engine A, Engine B, AnythingLLM) are assigned a `PriorityClass` of **`System-Critical`**.
* The DSPy Training pods and AlphaEvolve worker pods are assigned a `PriorityClass` of **`Background-Yield`**.

**What happens when you return:**
If the server is maxing out the RTX 5070 Ti doing AlphaEvolve training, and you suddenly type a prompt into AnythingLLM:

1. LiteLLM receives the prompt.
2. The Kubernetes scheduler sees a `System-Critical` resource request.
3. Kubernetes **instantly pauses/evicts** the `Background-Yield` training pods, flushing the VRAM.
4. Your prompt is answered in milliseconds.
5. The DSPy training job is placed back in the queue, waiting for the next 45-minute idle window to resume where it left off.

## 4. The Dynamic Phasing (Micro vs. Macro Downtime)

If Spectron attempts heavy GraphRAG consolidation on the NUC while Engine A is blasting thousands of DSPy inference requests over the network, the Gigabit LAN switch and the NUC's CPU will saturate. Because the system doesn't know if you are gone for 1 hour or 8 hours, it executes tasks in a strict two-phase order.

* **Phase 1: Micro-Downtime (First 1-2 Hours): The "Training" Phase**
    * *Why first?* DSPy prompt optimization runs entirely locally on the main server's GPU/RAM. It is highly interruptible. If it gets killed by Kubernetes Preemption because you came home, no data is lost. It just retries later.
* **Phase 2: Macro-Downtime (Hours 3+): The "Dreaming" Phase**
    * *Why second?* SurrealDB memory consolidation (GraphRAG connecting) requires sustained, complex recursive queries over the network. While interrupting this isn't dangerous (the NUC is UPS-backed and state-safe), killing a massive graph-traversal mid-flight wastes immense amounts of network bandwidth and NUC compute. We delay "Dreaming" until the system confirms a long-term idle state (like sleeping) to ensure these heavy network transactions complete uninterrupted.

## 5. Local CI/CD & Rollbacks

* **Gitea:** All agent configurations are version-controlled here.
* **Self-Healing:** Because the system trains itself chaotically throughout the day, it might occasionally "optimize" a prompt into something useless. If you return to work and notice NemoClaw acting strange, ArgoCD allows you to click one button and rollback the system prompt to yesterday's Git commit.
